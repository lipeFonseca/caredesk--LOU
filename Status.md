## Visão Geral (sem data — descreve o que o projeto é, não muda de lugar)

CareDesk é um sistema interno de acompanhamento pós-operatório de uma clínica. Um agente (ou o admin) cadastra o paciente, vincula um protocolo de contato, e o sistema calcula os marcos de acompanhamento. O scheduler diário gera notificação interna quando um marco vence.

**Escala do produto:** uma clínica, dois papéis fixos — `agent` (cadastro, contato, checklist de documento) e `admin` (tudo isso + protocolos, equipe, identidade visual). Multi-clínica foi avaliado e descartado (ver `2026-07-20`).

**Stack:** React 18 + Vite + Tailwind + Framer Motion (frontend) · Cloudflare Workers + Hono (backend) · Cloudflare D1/SQLite (banco) · Cloudflare R2 (arquivo) · JWT hand-rolled (Web Crypto, sem lib) + cookie `HttpOnly` (sessão).

**Ambientes:**
- Frontend: `https://caredesk-lou.pages.dev`
- Worker: `https://caredesk-worker.faugusto-thecoral.workers.dev`
- Local: frontend `http://localhost:5173` (proxy `/api` → `http://localhost:8787`), worker `http://localhost:8787`
- **D1 local e D1 remoto são bancos separados** — dado, credencial e migration aplicada num não existem automaticamente no outro (ver armadilha em `2026-07-22`).

**Regra de storage:** R2 pra binário grande (logo, background, avatar), D1 pra metadado/relação/permissão. Nunca usar R2 como fonte de dado cadastral/clínico.

  - **Por que não é SMTP:** Cloudflare Workers não abre conexão SMTP (bloqueio antispam da própria Cloudflare), então **senha de app do Gmail não serve** — ela só funciona para SMTP/IMAP. Decisão do usuário depois dessa constatação: **Google Apps Script publicado como Web App** faz a ponte. O rate limit conta o pedido mesmo sem conta existente, senão o próprio limite viraria o detector. Único desvio proposital: `429` real com `Retry-After`, porque sem ele o envio de e-mail vira a arma (flood na caixa da vítima + estouro de cota).

## 2026-08-10 — Importação de pacientes em massa via CSV

Usuário pediu uma forma de cadastrar vários pacientes de uma vez a partir de uma planilha, mantendo a estrutura pronta pra qualquer eventualidade futura (não um script de uso único). Três voltas de plano até fechar o escopo:

- **Plano 1 (rejeitado)**: parsing de Excel binário no navegador (`xlsx`/SheetJS) + tradução automática de nome de coluna. Usuário achou pesado demais pra uso único e preferiu inserir direto via banco.
- **Plano 2 (rejeitado)**: script de terminal de uso único. Usuário quer estrutura permanente, não script — "tenho a planilha editável, tudo que quero é alterar os nomes das colunas conforme temos hj no banco de dados e o sistema puxa as informações".
- **Plano 3 (aprovado, com ressalva)**: aba real do sistema, só CSV (texto puro, sem parsing binário), cabeçalho = nome literal da coluna no banco (`name`, `cpf`, `data_nascimento`, `procedure`, `surgery_date`, `responsavel`, `phone`, `email`), sem dicionário de sinônimo — o usuário edita a própria planilha pra bater. `id` nunca vem do arquivo, sempre gerado pelo sistema.

**Ressalva do usuário na aprovação**: "preciso de um monitor nessa aba, esse monitor deverá ser preciso e me informar quando o envio terminar e a taxa de sucesso e ser estremamente preciso não posso ter erros de pacientes faltando." Resolvido estruturalmente, não só na exibição: o desenho é **tudo-ou-nada** (`db.batch()` — ou o lote inteiro entra, ou nada entra, nunca "importou 480 de 500 e ninguém sabe quais 20 faltaram"), e depois do `db.batch()` o service reconta de verdade via `SELECT COUNT(*) FROM patients WHERE cpf IN (...)` os CPFs recém-inseridos antes de responder sucesso — mesmo princípio já em uso no projeto pra migration remota ("nunca confiar só no código de saída"), aplicado aqui a cada importação. Se a contagem não bater exato, devolve divergência em vez de mentir sucesso. O modal mostra os três números lado a lado (linhas no arquivo / linhas válidas / confirmadas no banco) e o horário exato de término.

**Validação reaproveitada, zero regra nova**: cada linha passa pela mesma validação que `POST /api/patients` já aplica — CPF com dígito verificador (`sanitizeRequiredCpf`), `ehMenorDeIdade` decidindo se `responsavel` é obrigatório (confirmado nos dois sentidos: menor sem responsável rejeita a linha, maior sem responsável passa normal), datas obrigatórias, protocolo único resolvido pra todo o lote, `assigned_agent_id` sempre quem importou.
